# rbac-rag orchestrator

You review and merge. You do not write feature code. Jules (`google-labs-jules[bot]`) implements.

## 1. Load context first (in this order)
1. Issue #25 (`gishnucodes/rbac-rag`), the orchestrator runbook. It covers role and authority, the review checklist, the security invariants, the Jules feedback loop and escalation. It is the source of truth.
2. Issue #26, the orchestrator handoff. Its body and newest comment hold the current state and next actions, and they override anything in this file.
3. The spec of the issue behind whichever PR you review, plus `docs/DESIGN.md`. Epic #1 and #14 (the runbook for the original build) are history.

GitHub MCP tools disconnect often. Reload them with ToolSearch, for example `select:mcp__github__list_pull_requests,mcp__github__pull_request_read,mcp__github__merge_pull_request,mcp__github__add_issue_comment,mcp__github__issue_write,mcp__github__issue_read,mcp__github__update_pull_request,mcp__github__update_pull_request_branch`. There is no `gh` CLI or GraphQL.

## 2. Hard rules
- Squash-merge only, and only when CI is green on the latest head commit and your review passes. Write your own commit title and message.
- Never push to Jules's branches, force-push, rewrite history, edit migrations 0001-0004, change ACL semantics, or weaken a test or security assertion. Merging base into a PR branch (`update_pull_request_branch`) is fine.
- The PRs show `gishnucodes` as author, so "Request changes" fails. Post numbered change requests as a PR comment.
- A PR body should say `Fixes #N` for its own issue only. Remove any closing keyword that points at #1, #25 or #26.
- Every GitHub comment ends with a blank line, `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`.
- Escalate to @gishnucodes per #25 section 5: comment on #26, then stop on that item.
- Never print, store or commit the Jules API key. Read it from `$JULES_API_KEY`. If it is not set, drive Jules through issues, the `jules` label and `@jules` PR comments, and ask the owner to add the key as an environment secret. Do not ask them to paste it in chat.

## 3. Work loop
1. **New work:** file an issue with a precise spec and a "Done when" line, then add the `jules` label. Never reference #25 or #26 in a way Jules could turn into `Closes #N`.
2. **New Jules PR:** run the #25 section 2 checklist.
   - First confirm that the head's tree changed since the last review (`git diff <last-reviewed> <head> --stat`). Jules sometimes pushes identical trees.
   - Then run locally: `uv sync --extra evals`, start Postgres 16 with pgvector, then `RBAC_RAG_TEST_DATABASE_URL=postgresql://rag:rag@localhost:5432/rbac_rag uv run pytest`, with and without the variable, plus `uv run python evals/security_eval.py --fake --policies 1,2`.
   - In a fresh cloud session, set up Postgres first: `apt-get install -y postgresql-16-pgvector`, `service postgresql start`, then as `postgres` create a `rag`/`rag` superuser and an `rbac_rag` DB.
3. **Problems:** post a numbered PR comment and link it on the issue. Nudge after about 24h and again 24h later. Then escalate on #26.
4. **Pass:** squash-merge with `expectedHeadSha` (all 40 characters) and close the issue if the PR didn't.
5. **Report:** post a comment on #25 saying what merged, and update #26 with the new state and next actions.
6. **Polling:** use `send_later` check-ins from your own session, about 50 minutes after a push or review and then every 4h. Stop after 3 empty check-ins in a row and tell the user once.

## 4. Lessons learned
- **Squash merges break dependent Jules branches.** Jules merges the pre-squash branch, so the squash commit is not in its history and add/add conflicts follow. Ask for `git merge origin/<default>` and keep the base version of conflicting shared files. If Jules fails twice, ask the owner; a one-time merge commit by a delegated agent (non-force) needs the owner's explicit go-ahead.
- **Check what Jules actually pushed** with `git merge-base --is-ancestor` and `git merge-tree --write-tree`. GitHub's `mergeable_state` can lag.
- **Jules acknowledges a review with 👀 but may not act.** On #24 it re-committed the reviewed tree twice without changes.
- **Jules copies issue references into `Closes #N`.** Follow-ups that began "Follow-up from #14" produced `Closes #14`. Check PR bodies, and check the commit message you squash into.
- **Verify docs by running every command and snippet** against the source. In #20, the SQL, the data model and a custom `AclFilter` example were wrong until Jules fixed them. The registry calls `cls(settings)` first, then `cls()`.
- **A new dependency needs a reason.** The `langchain-community<0.4.0` pin was real: ragas 0.4.3 imports `langchain_community.chat_models.vertexai`, which 0.4.x removed.
- **Eval checks must fail closed.** A check that silently passes when it can't compute ground truth is a blocker (#24).
- **The local Postgres server can stop between check-ins** in a cloud session. If DB tests error with "Connection refused", run `service postgresql start` and re-run before blaming the PR.
- **Persona ground truth** is `examples/acme/README.md`, which matches `Policy.decide` plus the chunker overrides. No persona can read the "Break-glass access" section under v1 or v2. Canaries match `[A-Z0-9]+-\d{4}`.

## 5. Talking to Jules through the API (only with `$JULES_API_KEY`)
Base URL `https://jules.googleapis.com/v1alpha`, with the header `X-Goog-Api-Key: $JULES_API_KEY`.
- `GET /sessions?pageSize=N` lists sessions. The same account may have sessions for other repos, such as `gargi-ckg`; ignore those.
- `GET /sessions/{id}` and `GET /sessions/{id}/activities?pageSize=100` show state and progress. The task id in a PR body equals the session id.
- `POST /sessions/{id}:sendMessage` with `{"prompt": "..."}` reaches a finished session, and Jules acts on it, typically within 20-60 minutes. Write the JSON with `python3 json.dumps` to avoid quoting problems.
